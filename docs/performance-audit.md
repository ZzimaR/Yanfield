# 长篇性能检查（2026-11-02）

本次使用 Windows、Node.js 24.15.0、Next.js 生产构建和独立 SQLite 测试库。未修改正式书稿，未调用付费模型。测试书稿分别为 5 万、300 万、1000 万字符，以及单章 10 万字符；字符数含标点，与界面的中文字数统计口径不同。

## 已修复

- 写作台目录请求使用 `view=summary`：SQL 不读取正文列。正文只为当前章单独请求；请求身份和取消机制防止快速 A → B → A 切换使用旧响应。保留原 API 默认行为以兼容现有调用方。
- 设定、章纲与 @ 引用选择器只请求章节摘要，不重复传输全书正文。
- 左栏页签首次打开时才加载，已访问页签保留状态；不再空闲时预加载全部隐藏页签。左栏用 React.memo 隔离正文输入引起的重复渲染。
- 目录每行菜单复用已有下标，消除循环内逐章 findIndex。
- AI 上下文先读取章节摘要；只为需要的前情摘要和显式章节引用读取对应正文，避免先读两遍整本书再裁剪。Agent workspace 也使用摘要树。
- 正文 diff 预计算归一化文本、跳过相同首尾，并限制中间 LCS 矩阵到一百万格。极长且整段重写时，中间区域按保守替换展示，可能降低局部匹配精度；完整接受和全部拒绝仍能正确还原。
- 底部状态条按自身容器宽度收起段落数、阅读时长、快捷键等次要信息，统计和保存状态不再挤成多行。

## API 实测

同一生产实例、同一测试库，预热一次后请求五次取中位数。读取完整 HTTP 响应，禁用传输压缩；下表为 UTF-8 JSON 大小，MB 按 1,000,000 字节计。耗时为本机回环端到端请求耗时，不代表实际页面可交互时间或远程服务器表现。

| 测试书稿 | 全文目录响应 | 摘要目录响应 | 全文 / 摘要耗时中位数 | 当前章响应 |
| --- | ---: | ---: | ---: | ---: |
| 5 万字符 / 10 章 | 152,884 B | 3,384 B | 3.88 / 2.75 ms | 15,250 B |
| 300 万字符 / 1000 章 | 9,269,150 B | 299,150 B | 61.17 / 10.67 ms | 9,264 B |
| 1000 万字符 / 2000 章 | 30,504,152 B | 604,152 B | 194.80 / 25.83 ms | 15,246 B |

千万字符目录负载下降约 98%。日常输入和自动保存仍按单章进行，书稿总字符数不会直接变成每次保存的负载。

## 验证与边界

206 项单元测试、TypeScript 检查和生产构建通过。新增回归覆盖默认会话标题、旧标题兼容、摘要投影、万段局部改稿、超过 diff 矩阵预算的完整接受与拒绝。浏览器已验证 300 万和 1000 万字符书稿输入后切章、切回，修改正确保存且没有串章；375px 手机、约 400px 窄正文栏和约 920px 宽正文栏的状态条 scrollWidth 均未超过 clientWidth。

这不等于已经保证“几百万字绝不卡顿”。以下问题仍需后续优化和正式帧率、输入延迟采样：

- 目录尚未虚拟化，1000 章页面约 2.16 万个 DOM 节点，2000 章仍可能有明显首次渲染开销。
- 档案页为判断哪些章节含正文，首次打开仍请求完整章节列表；现在不会在写作台首屏自动触发。
- Agent list 的章节全文查询、全局 LIKE 搜索仍会随书稿增长而变慢，尚未接入全文检索索引。
- 单章输入仍需序列化和统计当前整章；把几十万字放在一章，不能获得普通 2000–5000 字章节相同的输入性能。
- 长聊天记录及流式候选未做完整虚拟化，长会话需要单独压测。

建议按普通章节组织长篇；当前证据支持核心加载与章级保存路径的改进，尚未给出稳定 FPS 或输入延迟 SLA。
